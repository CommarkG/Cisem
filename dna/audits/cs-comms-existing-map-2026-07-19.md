## Per-element fork verdict → overall

The **NEW** is narrow and specific (the permission-Rings + cross-platform bus + the governed node itself). ## What this simulation TEACHES (the reusable lesson)
1. **The fork is PER-ELEMENT, not global.** A real creation is a *mix*; the map's job is to tag each element reuse/enhance/new. "Which branch?" is answered element-by-element, then summarized. This is more honest than one global label — and it's exactly the elimination insight: run the full map, and reuse/enhance/new fall out of it.
2. **The map's "why-relevant" line is the anti-freestyle safeguard** — it forces us to see §1.7 already IS the comms spec, so we'd be *consolidating a home*, not inventing comms. Titles alone would have hidden that.
3. **ENHANCE is the highest-risk branch** — reconciling ARCH-00350 to reference CS-COMMS (I10) touches a LIVE protocol; that edit needs a regression check ("did any live handoff break?"). This is where "don't harm what's verified" bites.
4. **The gap that matters:** the Active Archive isn't built — so the REJECT fork ("already ruled out?") currently has nothing to check against. That's a real dependency the flow surfaced on its own.
